# Terraform: AWS production infrastructure

```
terraform/
  bootstrap/        run once by a human: state bucket, GitHub OIDC provider, Terraform CI roles
  envs/prod/        the production stack (VPC, ALB+WAF, ECS, data host, secrets, IAM, alarms)
  modules/
    vpc/            3-tier VPC, NAT per AZ, S3 endpoint, flow logs, default-deny SG
    ecs-service/    Fargate service: task def, roles, logs, autoscaling, Cloud Map, circuit breaker
    data-host/      the EC2 that runs infra/docker-compose.yaml (encrypted disks, IMDSv2, SSM only)
```

## What gets built

| Layer | Resources |
|---|---|
| Network | VPC with public / private / data subnets in 2 AZs, one NAT per AZ (`single_nat_gateway = true` to save money), S3 gateway endpoint, VPC flow logs (1 year, KMS) |
| Edge | ALB (TLS 1.3 policy, HTTP to HTTPS redirect, unknown hostnames get 404, access logs, invalid headers dropped, deletion protection), wildcard ACM certificate for `*.bishnuthapa.info.np` validated and routed through **Cloudflare DNS**, WAFv2 (AWS managed rules, login and global rate limits, cookies redacted from logs) |
| Compute | ECS Fargate cluster; services `frontend`, `backend`, `auth-service`, `audit-service` with CPU autoscaling, rollback on failed deploys, non-root containers with all capabilities dropped |
| Data | One `t3.small` in the data subnet running `infra/`: separate encrypted data disk, no SSH (SSM Session Manager), IMDSv2 only, fixed private IP, DNS name `infra.edupulse.internal` |
| Discovery | Cloud Map private namespace `edupulse.internal`: `auth-service`, `backend`, `audit-service` |
| Secrets | Every password is generated by Terraform into Secrets Manager (KMS): one secret per service, so each ECS execution role can read only its own |
| Registry | 4 ECR repos: immutable tags, scan on push, KMS, lifecycle policy |
| Access | GitHub OIDC roles, no stored keys: `gh-push` (ECR push, from `main` only) and `gh-deploy` (ECS/infra deploy, only after the `prod` approval) |
| Alerts | SNS topic + alarms for ALB 5xx, unhealthy frontend, data-host status, ECS CPU |

Security groups follow one table (`flows` in `envs/prod/network.tf`): ALB to frontend to services to data host,
each on one port. Nothing else is allowed.

## Tagging standard

Every taggable resource carries these tags (the first seven come from the provider's `default_tags`,
so nothing can be forgotten; the rest are set on each resource):

| Tag | Example | Meaning |
|---|---|---|
| `Project` | `edupulse` | what it belongs to |
| `Environment` | `prod` | `prod` (`shared` for the bootstrap stack) |
| `ManagedBy` | `terraform` | do not edit by hand |
| `Stack` | `envs/prod` | which Terraform root owns it |
| `Repository` | `owner/repo` | where the code lives |
| `Owner` | `devops` | who is accountable (variable `owner`) |
| `CostCenter` | `edupulse` | cost allocation (variable `cost_center`) |
| `Name` | `edupulse-prod-backend` | human-readable name |
| `Component` | `backend`, `alb`, `waf`, `tls` | what the resource is |
| `Tier` | `edge`, `web`, `app`, `data`, `platform` | where it sits in the architecture |
| `Service` | `backend` | ECS services and their alarms, logs, roles and tasks |
| `DataClassification` | `internal`, `confidential`, `secret` | on buckets, the data volume and secrets |

- **Enforced in CI:** `tflint` fails the pipeline if `Project`, `Environment`, `ManagedBy`, `Stack`, `Owner` or
  `CostCenter` is missing (`terraform/.tflint.hcl`). `bash scripts/tflint-negative-test.sh` proves the rule fires.
- **ECS tasks** inherit their service's tags (`propagate_tags = SERVICE`, managed tags on), and the data host's
  volumes carry the host's identity, so cost and ownership follow the running things, not just the definitions.
- **Cost reports:** AWS only reports on a tag after you activate it. Billing > Cost allocation tags > activate
  `Project`, `Environment`, `CostCenter`, `Service`, `Tier`, `Component`.
- Not taggable: DNS records in Cloudflare (they carry a comment instead), routes and associations.
- Change `owner` / `cost_center` in `prod.auto.tfvars` if the defaults do not match your organisation.

## First-time setup

You need an AWS account, your domain on Cloudflare, and a GitHub repository.

```bash
# 1. state bucket, OIDC provider, Terraform CI roles (human admin credentials, once)
cd terraform/bootstrap
terraform init && terraform apply -var github_repository=OWNER/REPO
#    note the outputs: state_bucket, terraform_plan_role_arn, terraform_apply_role_arn

# 2. edit the CHANGE_ME values in terraform/envs/prod/prod.auto.tfvars
#    (cloudflare_zone_id, github_repository), then commit and push to GitHub
```

3. In Cloudflare, create an **API token**: My Profile > API Tokens > Create Token > template *Edit zone DNS*,
   restricted to the one zone `bishnuthapa.info.np`. The zone ID is on the domain's Overview page.
   In GitHub add the token as a **secret** named `CLOUDFLARE_API_TOKEN` (Settings > Secrets and variables > Actions).
   For a local `terraform plan`, export it as the environment variable `CLOUDFLARE_API_TOKEN`.
4. In GitHub, **Settings > Environments**, create three environments:
   `prod-infra-plan` (no reviewers), `prod-infra` (required reviewers), `prod` (required reviewers).
   The reviewers on `prod-infra` and `prod` are your approval gates.
5. **Settings > Secrets and variables > Actions > Variables**, add:
   `AWS_REGION`, `TF_STATE_BUCKET`, `TF_PLAN_ROLE_ARN`, `TF_APPLY_ROLE_ARN` (from step 1).
6. Push to `main`. The **terraform** workflow validates, plans, waits for your approval, and applies.
7. Add the remaining variables from the Terraform output `github_actions_variables`:
   `AWS_ROLE_PUSH`, `AWS_ROLE_DEPLOY`, `ECS_CLUSTER`, `ECR_REGISTRY`, `ARTIFACTS_BUCKET`, `INFRA_INSTANCE_ID`.
8. Run the workflows once, **in this order** (Actions > workflow > Run workflow, then approve `prod`):
   1. `infra` (starts MySQL/Redis/RabbitMQ on the data host, wait a few minutes after step 5 for its boot script)
   2. `auth-service`, `backend`, `audit-service`
   3. `frontend`
   From then on every merge to `main` that touches a service deploys just that service.

## Domain and subdomains

`app_subdomains = ["app"]` serves the web app at **https://app.bishnuthapa.info.np**. Terraform creates the
Cloudflare CNAME to the ALB and the certificate-validation records, so DNS needs no manual edits.
The certificate covers `*.bishnuthapa.info.np` and the apex, and the ALB answers 404 for any hostname
it does not know, so a stray wildcard DNS record can never expose anything.

- **More names for the same app** (e.g. `www`): add them to `app_subdomains` and apply.
- **Backend, auth and audit stay private on purpose.** They sit behind nginx, which checks the login on every
  request. Putting them on their own public subdomain would bypass that gate. They are reached internally as
  `backend.edupulse.internal` and so on.
- **A new public service** (for example a Grafana dashboard) needs its own target group and a host-based
  listener rule next to `aws_lb_listener_rule.app` in `envs/prod/edge.tf`, plus a CNAME. Ask and I will add it.
- **Cloudflare proxy (orange cloud) is deliberately off.** DNS-only keeps the real client IP intact for the login
  lockout and WAF rate limits. Turning the proxy on needs the Cloudflare IP ranges trusted in nginx and the ALB
  security group restricted to them first. Do that before switching it on, then set Cloudflare SSL mode to
  *Full (strict)*.
- `.info.np` must already be delegated to Cloudflare's nameservers at your registrar. If the Cloudflare dashboard
  shows the zone as *Active*, it is.

Passwords: Secrets Manager `edupulse/prod/auth` holds `ADMIN_PASSWORD` and `STUDENT_PASSWORD` (the app logins).

## Pipelines (`.github/workflows/`)

| Workflow | Runs on | Does |
|---|---|---|
| `backend` / `auth-service` / `audit-service` / `frontend` | changes in that service | calls `service-pipeline.yml` |
| `service-pipeline` (reusable) | called by the four above | `npm ci` + `npm audit` + syntax check, hadolint, build, **Trivy** image scan (fails on fixable HIGH/CRITICAL), SBOM; on `main`: push to ECR by commit SHA, **cosign** keyless signature, then **approval**, then ECS rolling deploy with automatic rollback |
| `infra` | `infra/**` | compose validation + shellcheck; on `main`: S3 sync, then SSM runs the deploy script on the data host (after approval) |
| `terraform` | `terraform/**` | fmt, validate, tflint, Checkov; on `main`: plan, approval, apply |
| `integration` | any service/infra change | boots the whole stack with Docker Compose and runs `scripts/smoke-test.sh` |
| `security` | PRs, `main`, weekly | gitleaks, CodeQL, dependency review |

Dependabot keeps actions, npm packages, base images and Terraform providers current.

## Known gaps

- **Secret rotation** is not automated (Checkov `CKV2_AWS_57` is skipped on purpose). Rotating means a rotation Lambda plus coordinated MySQL/Redis/RabbitMQ restarts.
- **Plaintext to the data tier** inside the VPC. Security groups are the only control (no TLS on MySQL/Redis/RabbitMQ).
- **Single data host.** Add EBS snapshots (Data Lifecycle Manager) and a `mysqldump` to S3 before holding real data. Its data volume has `prevent_destroy`, so `terraform destroy` stops there by design.
- **The data host does not auto-patch** (`ignore_changes` on AMI and user data). Use SSM Patch Manager or replace it deliberately with `terraform apply -replace=module.data_host.aws_instance.this`.
- **Terraform apply uses `AdministratorAccess`**, gated by approval and an OIDC subject condition. Narrow it once the resource set is stable.
- **GitHub Actions are pinned by version tag**, not commit SHA. Dependabot proposes updates, and SHA pinning is the next step.
- **Frontend runs with a writable root filesystem** because nginx renders its config at start.
- The apply job plans afresh instead of applying the reviewed plan file, because a plan file would carry secrets into a build artifact.
- WAF managed rules can occasionally block legitimate input. Watch the `aws-waf-logs-edupulse-prod` log group after launch.
